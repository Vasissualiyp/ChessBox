# M17.12 — The shapes above two dimensions: what can be a board, and what cannot

Companion to [`M17-geometry-view.md`](M17-geometry-view.md), §M17.12. Records the first
implementation (the `torus3d` and `hyper4` shapes) and the feasibility study the plan asked
for on the `t6` quintic.

## What "playable in the same way" requires

The 2-D geometry view works because `PlaySurface` produces three things off one sampling
and they cannot disagree:

1. **a patch per cell** - the square as a piece of the surface, drawn as a mesh;
2. **a seat per cell** - where a piece stands and which way is up;
3. **a picker** - the ray tested against the same tiles, nearest hit wins.

plus the **adjacency invariant**: two cells adjacent in the lattice are adjacent in the
drawing, and two that are not, are not. A shape that breaks it is a picture, not a board.

For a surface (2 real dimensions) embedded in the 3-D world, all of this is honest. Above
two dimensions the drawing is a *projection* of a higher-dimensional lattice into 3-D, and
that is where it gets hard.

## The dimension problem

A `d`-dimensional manifold cannot be embedded in 3-D once `d > 3`, and even `d = 3` cannot
be embedded *flatly* (a flat 3-torus has no isometric embedding in R³). So every shape
above two dimensions in this project is a **self-intersecting immersion**: distinct cells
land on top of one another. That has three consequences:

- **Coincident tiles.** Distinguishing two cells that project to the same point needs
  something other than position (a shell index, a slice, a ghost).
- **Hidden tiles.** The picker returns the nearest sheet, so a cell behind another is
  unreachable by a click - which is correct for a picture and wrong for a board that must
  let you select *that* cell.
- **Adjacency.** Lattice neighbours that differ only along a folded axis may not be near
  each other in the drawing.

None of this makes the shapes useless; it makes them **deliberate modes** whose limits must
be stated, not defaults.

## The first implementation: `torus3d` and `hyper4`

Built, keyed by the variant's own name (`playShapePosition`, `src/render/overture_scene.cpp`)
because a shape above two dimensions is *authored*, not read off the gluing - `hyper4` is a
plain 4-D box with no identifications at all.

- **`torus3d` — nested shells.** `shellTube` at the point the library screen has fully
  rolled: the file and rank gluings close a T² surface (the shell), and the level axis
  becomes the shell radius, so four levels are four nested shells about one core circle.
  The file/rank adjacency is carried faithfully by the shell; the **level** adjacency is
  carried by *which shell*, which reads clearly but is not Euclidean nearness.
- **`hyper4` — the tesseract.** The 4-cube projected the standard way, the aeon axis being
  the nesting. The inner and outer cubes overlap; picking takes the nearest sheet.

`PlaySurface::buildStacked` places one flat tile per cell from `playShapePosition`, sized
from its neighbours, and the picker tests each tile. Tests: a tile and a seat per cell, unit
normals, a non-degenerate extent, a pick round-trip, and validation-clean GPU renders
(`gui-geometry-torus3d`, `gui-geometry-hyper4`).

**Known limits of this cut.** The level (torus3d) and aeon (hyper4) axes are not adjacent-
in-the-drawing; INVERT and slide are not offered for these shapes yet (`buildStacked`
ignores the pose); and the hidden-sheet problem is unaddressed. They are a first pass, not
the finished shapes.

## The `t6` quintic: the honest answer

The plan asked whether the Calabi-Yau quintic (`src/render/quintic.hpp`) could carry the T⁶
lattice as a playable manifold. **It cannot, and the reason is dimension, not taste.**

- A 6-torus is 6-real-dimensional; the quintic's standard picture
  (`quinticPoint(k1, k2, x, y) -> 3D`) is a projection of a 6-real-dimensional object into
  3-D. It cannot be injective.
- The `t6` overture already demonstrates the fold: it tiles **25** quintic patches
  (`k1, k2 ∈ 0..4`) × **4 × 4** in-sheet cells (`u, v`) = **400** tiles, for the lattice's
  **4⁶ = 4096** cells. That is a ~10:1 collapse - roughly ten lattice cells per drawn tile.
- The quintic therefore carries adjacency along **two** of the six axes (the in-sheet `u`,
  `v`); the other four are folded into the patch index and are not represented as
  adjacency at all. The adjacency invariant fails by construction.

So a playable quintic, in the sense the 2-D surfaces are playable, **does not exist** as a
single 3-D object. The overture's caption already says as much ("the quintic is not this
board's own space").

### What *could* be built, honestly

If a `t6` "shape" is wanted, it must give up the full embedding and take one of:

1. **Keep the lattice (recommended default).** The game already plays `t6` as a grid of
   boards (`view::layout`'s grid axes), which is a faithful, pickable, adjacency-preserving
   view. The quintic stays a library animation. This is M17.4's "extrude the lattice", and
   it is the only *board* here.
2. **A sliced quintic view.** Show a 3-D cross-section of the quintic at a time, with a
   scrub control over the folded axes, so each slice is an injective picture and the picker
   disambiguates within it. This is the same trick the board already uses for the extra
   axes, applied to the quintic: faithful per slice, not globally. Cost: a slice control and
   a per-slice adjacency check.
3. **An interactive immersion with overlap tolerance.** Draw the full collapse and rely on
   nearest-hit picking plus a ghost/slice control to reach hidden cells. Cheap and visual,
   but it is a picture; the interface must say so.

### Verdict

- `torus3d` and `hyper4`: a first shape **is** built and playable, with the level/aeon
  axes' adjacencies stated as limits.
- `t6`: a faithful full embedding is **impossible**; a sliced quintic view is possible and
  honest. Recommended order: finish the 3-D shapes (slide/invert, hidden-sheet handling,
  adjacency tests), then, if a `t6` shape is still wanted, build the **sliced** view (option
  2) rather than the collapse. Do not ship the overture's collapse as a board.
